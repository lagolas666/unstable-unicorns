## 2. Снятое подозрение: три записи `reshuffle` вместо одной

В прошлом заходе кейс R1 давал **3** записи `event:'reshuffle'` на один добор. Причина — старая фикстура, а не движок.

Фактический журнал на чистом коде (R1, пустая колода + сброс из 3):

```
R1 pending=undefined logs=[["debug",{"event":"reshuffle","size":3}],
                          ["play",{"cardId":"unicornotopia_spell","name":"Единороготопия"}]]
```

**Ровно одна** запись. Три записи были следствием того, что сброс в прежней фикстуре собирался из карт, уже лежавших в руке/стойле, и решафл срабатывал повторно на каждом цикле добора. Ожидание «ровно 1 запись» подтверждено, менять его не потребовалось.

## 3. Новый тест: `reshuffleLive.test.ts`

3737 байт, CRLF=89, loneLF=0, U+FFFD=0, sha256 `fa49d8f05ddda38d…`.

Идёт настоящим путём: `POST /api/game/test/create` → `POST /api/game/:id/play` картой md 127 → при наличии окна `pending.kind='play'` закрывает его через `resolvePending` → читает журнал из `store.games.get(id).logs`.

### R1 — решафл срабатывает
Шаги:
1. Колода `[]`, сброс `['u1','u2','u3']`, у p1 в руке `unicornotopia_spell` (on_play: `draw_until_limit` для self, лимит руки 7).
2. `POST /play` картой.

Ожидаемое: 200; ровно один `reshuffle` с `size: 3`; сброс пуст, в сбросе остаётся только сыгранное заклинание; в руке 3 карты.
Фактическое: совпало.

### R2 — контроль: решафл не нужен
Колода из 8 карт, сброс пуст: добор до лимита 7 идёт из колоды, `reshuffle` — 0 записей.
Ожидаемое и фактическое: 0 записей.

> Замечание по методике: `draw_until_limit` вычерпывает и непустую колоду, поэтому контроль построен на разнице «хватает карт до лимита / не хватает», а не на самом факте добора.

## 4. Переписано: `executorDeckEmptyGuard.test.ts`

Старый первый кейс держал отменённое поведение (`ожидание discard === ['x1','x2']`, комментарий «перетасовки нет»), describe утверждал ложное. Приведено к текущему правилу: сброс перетасовывается, конец партии — только когда пусты **и** колода, **и** сброс.

Ключевая деталь фикстуры: сброс из **3** карт при доборе **2** — после решафла в колоде остаётся 1 карта, партия продолжается.

> Первая редакция использовала сброс из 2 карт и получала `winnerId='p1'`. Это не баг: после добора обе зоны пусты, и победа по лидеру единорогов — штатное правило. Ассерт был неверен, а не движок; исправлена фикстура.

Также в `makeCtx` добавлен `logs: []` — без него решафл молча не пишет журнал (запись под `if (Array.isArray(ctx.logs))`). Тест был красным именно на чтении журнала, физика зон при этом уже была верна.

Факт: 5567 байт, LF 99, CRLF=0 (родной стиль файла — LF), U+FFFD=0, sha256 `1164eeef8727d4f1…`. Второй кейс (обе зоны пусты → `winnerId='p1'`) оставлен без изменений.

## 5. Мутационная проверка (невакуумность)

Мутации в `src/engine/executor.ts` (`reshuffleDiscardIntoDeck`), прогон двух файлов вместе:

| Мутация | Правка | Результат | Откат |
|---|---|---|---|
| M1 | решафл отключён: `deck.length >= 0` в условии выхода | 2 failed / 2 passed — краснеют R1 и первый кейс deck-guard, R2 и контрольный кейс живы | BYTE_IDENTICAL |
| M2 | решафл поднимает 1 карту: `st.discard.slice(0, 1)` | 2 failed / 2 passed — те же два | BYTE_IDENTICAL |
| M3 | событие журнала переименовано в `'reshuffled'` | 2 failed / 2 passed — те же два | BYTE_IDENTICAL |

Контроль на чистом коде: 4 passed / 4 total. Итоговый sha `executor.ts` после всех откатов — `74256c4ad4511cf3…`, идентичен исходному.

В каждом прогоне гибнет ровно по одному тесту в каждом сьюте: покрытие реальное, контрольные кейсы не ловят мутации (значит проверяют именно то, что должны).
