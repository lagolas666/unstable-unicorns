# План: словарь эффектов, привязываемый к любой карте

Дата: 03.11.2026. Автор: Единорог Аналитик. Решение Даниила: «эффекты, которые можно привязать к любой карте — делай как надо».
Статус на 05.11.2026: **стадия 1 закрыта** (`docs/effect-coverage.md`, 62 из 62 числовых ячеек сверены с каталогом), стадия 2 выдана Бэкенду. Гейт после правки доков: jest 35 сьютов / 389 passed / 3 skipped, EXIT=0; tsc EXIT=0.

## 0. Почему порядок изменён

Прежний план начинался со снятия 34 строк хардкода по имени карты. Замер 03.11.2026 показал, что это лечит симптом:

| Слой | Знает | Источник |
|---|---|---|
| `server/data/catalog.v2.json` | **43** kind, **19** триггеров | данные |
| `server/src/engine/executor.ts` | 27 kind (5 из них — селекторы, не действия), 5 триггеров | код |
| `shared/src/types.ts` → `ActionKind` | 25 значений (без `draw`, `pull`, `force_discard`, `return_to_hand`) | контракт |
| `shared/src/types.ts` → `Trigger` | 13 значений | контракт |
| `server/src/models/card.ts` → `TRIGGERS` | 13 значений (другой набор!) | схема БД |

Следствие замера: **54 карты из 154 эффектных имеют нерабочее поведение** — у них мёртв хотя бы один kind или триггер (49 карт по kind, 20 по триггеру, пересечение 15, объединение 54). Знаменатель — 154 карты с непустым `effects`, а не 329: у 175 карт каталога действий нет вовсе (95 детёнышей, 73 базовых единорога, 7 карт описаны только текстом).

Если снять хардкод первым, эти карты не получат ничего: заменять хардкод-блок нечем, словарь пуст. Поэтому порядок инвертирован: сначала движок умеет исполнять данные, хардкод отпадает сам как следствие.

## 1. Три пояса мёртвого кода

Живой исполнитель — это `case` в `switch(action.kind)` или сравнение `action.kind === '...'`. Форма `{ kind: 'pull' }` внутри хардкод-блока исполнителем не является.

**Без исполнителя — 21 kind (55 вхождений «карта×kind», это 49 уникальных карт):**
`reactive_trigger` (10), `cancel` (9), `prevent` (8), `choice` (6), `modify_action` (3), `scry` (2), `restrict_action` (2), `force_play` (2), `mega_shuffle`, `copy_effects`, `peek`, `conditional_loop`, `pass_hands`, `mill_until`, `draw_conditional`, `skip_turn`, `draw_until_limit`, `redirect_target`, `choose_card_type`, `choose_players`, `modify_hand_limit` — все по 1.
Сверка состава: 8 kind с 2+ вхождениями дают 42, 13 единичных дают 13, итого 55 — сходится.

**В обход switch (исполняются, но не в контракте) — 4 kind:**
`draw` (22 вхождения, 21 карта), `pull` (6), `force_discard` (8), `return_to_hand` (6). Код их знает специальными ветками до `switch` (`executor.ts` L656–662, L952–962), а `ActionKind` их не содержит — типовая проверка на них падает, схема может отбросить.

**Без драйвера — 13 триггеров (20 карт):**
`on_would_be_destroyed` (4), `on_opponent_play` (4), `on_opponent_plays_unicorn` (2), `on_would_be_destroyed_or_sacrificed`, `on_opponent_unicorn_effect`, `on_leave_stable`, `on_opponent_pull_baby`, `on_opponent_plays_upgrade_downgrade`, `on_any_unicorn_sacrificed_or_destroyed`, `on_opponent_plays_neigh`, `on_opponent_plays_spell`, `on_opponent_sacrifices`, `on_opponent_would_draw`.

`on_turn_end` **не** в этом списке: цикл есть, `gameService.ts:787`. `while_in_stable` тоже не мёртв целиком — читается в `unicornTypes.ts:84` как маска, но аура не исполняется; выносится в стадию 4 отдельным пунктом.

## 2. Стадии

### Стадия 1 — карта исполнения по каждому kind (Бэкенд, 1 день, без правок кода) — ВЫПОЛНЕНА 03.11.2026

Выход: `docs/effect-coverage.md` — таблица 43 kind × колонки `executor` / `gameService.react` / `hardcode` / `никто`, и то же по 19 триггерам. **Сдана, проверена замером: 62 из 62 числовых ячеек совпали с каталогом.**

**Зачем первой:** часть мёртвых kind может исполняться реакционным слоем `gameService` (`react/neigh`, `react/super_neigh`, `react/redirect`, `react/shield`, `react/hypnorog`, `react/rewind`, `react/intercept_steal`), а не executor. `cancel`, `prevent`, `reactive_trigger` — вероятные кандидаты. Пока это не проверено по коду, число 68 завышено, и планировать стадию 2 нельзя.

Готово когда: для всех 43 kind и 19 триггеров в таблице проставлен исполняющий файл со номером строки, либо «никто». Каждая строка «никто» подтверждена поиском по всему `server/src`, а не только по executor.

**Результат стадии 1:** живых kind 22, мёртвых 21; живых триггеров 6, мёртвых 13. Реакционный слой (`react/*` — 14 методов) `kind` карты не читает вообще, поэтому `cancel` / `prevent` / `reactive_trigger` остаются мёртвыми: отмена работает по `instant_subtype` и `cancelLevel` окна, а не по данным карты.

### Стадия 2 — контракт данных (Бэкенд, 1 день)

Одна правка, ноль поведения: привести словарь к данным.

- `shared/src/types.ts`: `ActionKind` += все 43 значения (сегодня 25: не хватает 4 обходных и 14 из мёртвого списка, при этом есть `prevent`/`cancel`/`ignore`/`transfer`/`protect`/`grant_immunity`/`goto_end_turn`, которых в каталоге v2 нет); `Trigger` = ровно 19 значений из каталога.
- `server/src/models/card.ts`: `TRIGGERS` берётся из того же источника, что `Trigger` (сейчас два разных набора — `while_in_stable` есть в одном и отсутствует в другом).
- `Action`/`Effect` получают `quantity.mode` (`exact` | `up_to` | `all` | `random`), `optional`, `condition`, `target.filters.unicorn_type`, `mask`.

**Главный блокер стадии 2, найденный при проверке стадии 1:** `models/Card.ts` → `TRIGGERS` содержит 13 значений (`immediate`, `on_play`, `on_discard`, `on_destroy`, `on_turn_start`, `on_turn_end`, `while_in_stable`, `when_other_plays`, `after_resolve`, `on_enter_stable`, `on_sacrifice` + 2 служебных импортёра), и **ни одно из 13 мёртвых значений каталога в нём не валидно**. Если заливать каталог через модель, все `on_opponent_*` и `on_would_be_destroyed*` отбросятся при сохранении. Схему править в этой же задаче, иначе стадия 4 упрётся в потерю данных.

Готово когда: тип `ActionKind` содержит 43 значения, `Trigger` — 19, наборы в `shared` и `models/card.ts` совпадают побайтово по составу; `tsc` EXIT=0; jest на baseline (35 сьютов / 389 passed / 3 skipped, EXIT=0) — поведение не изменилось; карточка из каталога с `kind: 'force_discard'` проходит `new Card(...).validateSync()` без ошибки.

### Стадия 3 — исполнители по группам (Бэкенд, по одной группе за задачу)

Порядок — от простого к сложному, каждая группа отдельной задачей со своим тестом:

1. **Добор и поиск:** `draw_conditional`, `draw_until_limit`, `mill_until`, `scry`, `peek`, `mega_shuffle`.
2. **Перемещение:** `return_to_hand`, `pass_hands`.
3. **Ход:** `skip_turn`, `modify_action`, `restrict_action`, `modify_hand_limit`, `force_play`.
4. **Выбор:** `choice`, `choose_card_type`, `conditional_loop`, `copy_effects`, `redirect_target`.
5. **Реакции:** `reactive_trigger`, `cancel`, `prevent` — только после стадии 1 выяснится, что из них уже живёт в `gameService`.

Готово по каждой группе: новый тест на каждый kind, красный до правки и зелёный после; полный гейт на baseline; мутация «kind вырезан из switch» роняет именно тест этого kind.

### Стадия 4 — триггеры (Бэкенд, по одному)

`while_in_stable` первым (24 карты, на нём же маски и аура), затем `on_turn_end`, `on_leave_stable`, `on_would_be_destroyed*`, затем группа `on_opponent_*` вместе с окнами реакции.

Готово когда: карта с триггером в данных срабатывает без хардкода; тест проверяет срабатывание и молчание при невыполненном условии.

### Стадия 5 — хардкод как следствие

Когда данные покрывают карты из 20 хардкод-блоков, блоки удаляются по одному, каждый со сверкой «до/после совпадает» на полном гейте. Отдельной задачи «снять хардкод» нет: это проверка того, что стадии 3–4 сделаны.

### Стадия 6 — админка карт

После стадии 5: экран, который собирает карту только из словаря стадии 2 и не требует правки кода.
